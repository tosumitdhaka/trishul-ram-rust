## License and dependency provenance — binding Phase 0 decision

**Proposed target repository license: Apache-2.0**, matching the Python reference project's declared license; user/project-owner approval of this selection is part of the Phase-0 sign-off. No existing Python source, generated compiled MIBs, UI assets, third-party code or bundled fixtures may be copied into the new repo **without** identifying individual provenance, license/SPDX, copyright and redistribution obligations. Native `trishul-snmp` is documented MIT and can be consumed as a dependency with attribution/license notices; a dependency must not be vendored merely for convenience. Before first P1 source commit, add repository Apache-2.0 LICENSE, SPDX policy and a reproducible Cargo.lock/dependency license inventory; reject a dependency with incompatible or unclear license. Test data under Python reference must be treated with the same provenance checks; newly authored P1 fixtures in this design branch are independent. No legal guarantee is implied by this engineering review.

## Security re-entry gates and fail-closed principle

- Any future API listener must have an explicit bind address, secure default, transport authentication and identity-based authorization. `0.0.0.0` + auth disabled is **not** an allowable default.
- Production mode cannot accept `unsafe_dev=true`; tests must fail startup even if address resolves to 127.0.0.1 when production profile is enabled.
- Remote worker credentials are provisioned out-of-band via per-role CA/pinned workload identities, do not originate from an unauthenticated handshake, and are independently checked alongside short-lived attempt authorization. Bootstrap credential distribution/certificate issuance is unresolved implementation detail subject to P4 design review, **not** permission to weaken the invariant.
- Secrets supplied through environment/file manager are never included in plan hashes, logs, event labels, open telemetry attributes, exception messages or user-visible schema. Define credential reference materialization and lifetime before shipping a plugin needing secrets.
- If any deferred detail would change an accepted early-phase invariant, that phase is blocked until a new ADR is reviewed; the deferral is not a carte blanche implementation decision.

### Exact proposed superseding D03/D07 clause (NOT ACTIVE UNTIL NEW DCR APPROVED)

**D03-SNMP-P3 / proposed supersession of D03 timing, only for SNMP+JSON:** "The **generic non-SNMP** binary/decimal/timestamp JSON serializer mapping remains **DEFERRED TO P5**. **Before a P3 SNMP+JSON capability may be advertised or admitted**, the SNMP adapter must have a **versioned deterministic field-level binary-safe OctetString representation independently proven against pinned Python** `ff380725b86c9569901ea89ad6771623847cc4e2`, covering empty bytes, non-UTF-8, embedded NUL, trap metadata and the full unsigned Counter64 range through `2^64-1`. Ambiguous per-record coercion, implicit UTF-8 and float conversion are forbidden; lack of proof means pre-effect capability rejection. **DATA-02 is a P3 capability-admission gate, not a P2 implementation item or P1 retroactive requirement.** The remaining D03 P5 deferral stands."

**D07 / proposed capability addendum:** "Pin schema/producer and compiled MIB provenance under existing D07. A tested SNMP library and accepted MIB bundle do **not** by themselves authorize SNMP+JSON; gate its capability advertisement on **DATA-02** with specific versioned field types, OctetString oracle bytes, v1/v2/v3 trap metadata and precision-preserving Counter64 output. Unsupported combinations reject before any effects."

This proposed text explicitly identifies the narrow precedence it would acquire **only after independent DCR review and an Orchestrator immutable-SHA decision**; the frozen D03/D07 rows above remain the active contract in the meantime. Detailed proof and exclusion model: [ADR-016](proposals/adr-016-serialization-sources-persistence-gates.md).
